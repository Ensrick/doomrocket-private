# Under-barrel crystal flame: issue #15

Updated 2026-10-14 (America/Chicago). Crunch's repeated written verdict and
in-game screenshot reject the native green ground-fire sizing candidate: it
remains far too large. Published TEST v0.1.90-dev includes the temporary
particle omission prepared for the unpublished v0.1.89-dev, preserving the
crystal and artist assets. His reference is a
small flame close to the crystal. No reliable all-map replacement is established.
The measurements and earlier candidates below retain their historical evidence.

The 0.010 value shown by the old command was our Lua minimum clamp, not an
established engine limit. The dormant scaled-link experiment reports its inputs
and link scales without promising rendered dimensions or a successful resize.

The actual crystal is present in the accepted launcher. Read-only Blender
inspection of Crunch's SHA-pinned scene identifies the faceted, 75-vertex
component **1858–1932** under the muzzle. Component 1933–1981 is its mounting
socket, not the crystal; the unrelated component 3259–3307 is beneath the main
chamber. No new locator, mesh replacement or guessed muzzle offset is needed.

The same indices survive in the shipping 3,308-vertex launcher FBX. The
[measured fixture](../../tools/fixtures/warlock_crystal_anchor.json) retains the
crystal centroid, tip cluster, mounting-cap landmark, dimensions and right-handed
frame. `tools/tests/test_doomrocket_crystal_anchor.py` checks the real FBX hash,
coordinates, exact connected component and frame. Generated highlighted views
are in ignored `.build/issue15_crystal/{side,underside}.png`.

The frame is in engine root metres, **not native node-local coordinates**.
The accepted compiled `pRocketLauncher` node (index 7) has scale 100. The effect
must convert through its verified inverse rest world transform, then follow that
live mesh node; do not apply a posed hand-bone inverse or normalize away scale
compensation. Use the exact current inventory launcher, not a dropped replacement.

## Effect selection remains unresolved

The installed native `fx/wpnfx_warp_fire_nozzle` resource is a candidate, not an
accepted match to the reference. Its resource hash appears at byte 1900 in the
Warpfire package table (`resource_packages/breeds/skaven_warpfire_thrower`;
3,837 bytes). Decoding identifies one continuously emitting billboard cloud,
capacity 10, a +X velocity cone at 3.5–4.5 m/s, and a 0.1 m spawn sphere.
SHA-256: `da0400ae2f2fb959096c5af5015f65b0e925e46d28348b18c1439c7571e94db3`.
The resource lifetime is 1,410,065,408 seconds, effectively persistent for a
game session. Its material/curve appearance has **not** been visually verified.

`fx/wpnfx_warp_fire_flames` is also in that package (resource hash at byte 1932),
but the current particle reader encounters unsupported initializer data.
`fx/skaven_torch_warpfire_01` has a three-cloud persistent effect but is not in
that breed package. Neither effect's name proves correct size or appearance.
No native bytes were copied into the mod and no guessed effect was enabled.

The acceptance target is a small green flame appropriate to the reference, with
one effect per live owner/current launcher on each peer, no recreation per frame,
stop before death/drop/inventory teardown, and forget before world release.
Keep #15 open until Crunch accepts its placement, appearance, and persistence.
A solo written verdict is sufficient; there is no separate multiplayer gate.

## Candidate implementation (2026-10-07)

`extensions/doomrocket_crystal_flame.lua` links `fx/wpnfx_warp_fire_nozzle`
(Warpfire Thrower package, already resident for the rocket exhaust) to the
carried launcher's `pRocketLauncher` node, one effect per live launcher on each
peer. It follows the accepted backpack smoke lifecycle: started with the
inventory setup, stopped at death, drop, item disable, inventory destroy/freeze
and mod reset, forgotten before world release, and the package reference is
this module's own.

The pose is `utils/doomrocket_crystal_anchor.lua`, generated by
`tools/build_crystal_anchor.py` as inverse(compiled node rest world) times the
measured tip frame. The compiled node is a scale-100 frame at the unit root
(about 1.6e-5 rad of rotation), so the anchor carries 0.01-scaled axes, like
the chimney and hose endpoints. Its +X runs from the mounting cap to the tip,
which is the effect's emission axis. `--check` regenerates it against the
current clean build and the fixture's reviewed unit hash.

Effect choice is still a candidate: the nozzle emitter's look, size and
direction on the crystal need an in-game verdict, and a different effect or a
rotated frame may be needed.

## v0.1.84 effect change (2026-10-07)

Crunch's v0.1.83 report: no flame visible. The log shows the nozzle effect was
created on every Engineer (`[doomrocket:CRYSTAL] phase=start`) and stopped at
death, and the chimney smoke, which uses the same 0.01-scale link convention on
a scale-100 node, is accepted in game, so the effect itself is the suspect: vanilla

`warp_fire_flamethrower_remains_size` particle variable (radius, height; the
damage blob starts at 0.6, 1.2). The pose permutes the anchor to (y, z, x) so
the effect's rising +Z runs along the crystal. Default size 0.06 x 0.2 m; the
TEST command `/warlock_crystal_flame <radius> <height>` resizes live flames for
tuning.

## Size failure and rejected scaled-link candidate (2026-10-10)

[Crunch's v0.1.84 report](https://github.com/Ensrick/doomrocket-private/issues/15#issuecomment-6054610629)
accepts visibility, rejects sizing, and suggests the torch fire. The matching log
shows the command running with values from 0.01 to 2.0, including new emitters
created at those values. This is an implementation failure, not missing tester
steps. His screenshot shows a broad green fire obscuring the launcher.

The inspected native ground fire payload has SHA-256
`794d8e51dc396b8a086afddd5c4b09191aa8e5349951d124e7691d4d677e8262`
and four clouds. Its flame spawn cylinder uses a fixed
0.6 m radius, its initial billboard size is about 0.89–1.51 m, and its cylinder
initializers do not bind a particle variable. The native size variable exists,
but changing it does not scale every cloud. It cannot serve as the controller's
whole-effect size contract.

The historical candidate follows VT2's native `VortexExtension` and
`VortexHuskExtension` pattern: `Matrix4x4.set_scale` on the local attachment pose,
then `World.link_particles` with that scaled pose. The
[Stingray World reference](https://help.autodesk.com/cloudhelp/2019/ENU/Max-Interactive-Help/lua_ref/obj_stingray_World.html)
defines the link pose as the effect's new local coordinates relative to the
parent scene node. The reference radius is 0.6 m and reference height is vanilla's
mature 1.2 m fire target; default 0.06/0.2 inputs produce link scale
(0.1, 0.1, 1/6). These are approximate visual targets, not guaranteed rendered
bounding-box measurements.

The generated frame's 0.01 inverse-node scale remains intact and cancels the
compiled scale-100 wrapper. Its axes are multiplied by the visual scale; the
default local link scales are therefore approximately (0.001, 0.001, 1/600),
while its tip translation remains unchanged. The engine's native attachment
follows the current launcher mesh scene pose automatically. It is never
recreated or manually moved every frame. This avoids relying on the unlinked
`move_particles` API, which affects only newly emitted particles, and avoids a
second world-transform composition convention in the controller.

In the dormant experiment the tuning command destroys and recreates only the live emitters on this peer,
so old particles cannot obscure an immediate size comparison. It reports how
many emitters were recreated and logs both scale axes; rendered size remains unverified. New Engineers inherit the
same setting. Invalid/non-finite inputs are rejected and numeric inputs remain
bounded. Death, item removal, reload, and world teardown retain explicit cleanup.
The native `destroy` link policy destroys the effect when its launcher is deleted;
the controller then forgets its ID without querying a potentially recycled
handle. The pre-world-release hook forgets the handle before engine teardown.

`tools/tests/test_doomrocket_crystal_flame.py` executes the production controller
with strict particle, package, and world lifetime doubles. It checks actual scale
in the actual link pose, world-anchor compensation on a rotated/translated
scale-100 launcher, native following without respawning, immediate
resize, deletion cleanup, and zero particle access after world release. These
checks establish the API/lifetime contract, not the flame's visual acceptance.

### Torch reuse investigation

The existing native `fx/skaven_torch_warpfire_01` is a persistent three-cloud
effect (4,000 bytes, SHA-256
`b19c5d4659638d6a6b8e5a456b7f474e6fc2c8867b470c5e97665200e91216b3`).
It has no particle variables; its flame cloud has 1–2 m initial billboard sizes,
so it also needs explicit scaling for this crystal. A local extracted donor was
inspected read-only; no native art payload was added to the repository.

It is present in level packages, including Skittergate, but absent from
`resource_packages/breeds/skaven_warpfire_thrower`. Its three material IDs
(`E379EEEC28C7D5DD`, `AC14E04B4F4F5C4D`, `0B3A1E26F36391AB`) are absent from that
breed package too. A string swap would therefore depend on the map's resource
residency. Loading an entire unrelated level solely for this effect is unsuitable.
Consistent torch reuse would require a separately verified native effect/material
dependency packaging change. The scaled ground-fire attempt did not correct the
reported visual failure and remains disabled in published TEST v0.1.90-dev. A resource name
swap alone does not establish residency or an appropriately small visible flame.


### Unactivated small pickup-torch option (read-only audit, 2026-10-13)

`fx/wpnfx_torch_local_space_3p` is a separate **unactivated prototype option**,
not a flame fix in v0.1.90-dev. Its existing 1,253-byte payload has SHA-256
`b09f353565dfcc9dbe51a55b23fe488275f142b1b5b36c749b5dbb95fe958cce`.
The decoded resource has one billboard cloud, capacity 40, a `local_space`
simulator and persistent lifetime. Its initial size-channel range is 0.10-0.20,
with cylinder radius 0 and height -0.10-0.00. These are native initializer
parameters, not rendered bounds or a promise of metre-sized output. An
unchanged codec decode/assemble is byte-identical; opaque curves remain intact.

A typed-table audit of native `resource_packages/pickups` (7,837 bytes, SHA-256
`985d8add0ffc56998ca4776fb45f1ff91527e17e771793bc30e6718bc87fba64`)
finds each identified direct dependency exactly once: particle
`3DB3CE6438D57683`, child material `A0EC15D2679F209F`, parent material
`EF52A5800BEB269E`, and texture `73548ADEE6C02173` (`fx/textures/anim_smoke_4x8`).
The decoded child points to that parent and texture; the parent exposes no
additional texture bindings. Game boot source loads the pickup package with its
`global` reference. A prototype must still check native availability and own
its package reference without unloading the game's reference. This evidence
identifies a smaller existing effect and its direct dependency chain; it is not
a runtime residency or renderer pass on the current installation.

Colour, rendered size, billboard orientation and the target's small green-flame
appearance remain unverified. The validated material parser exposes no RGB/RGBA
tint parameter for this child, and the particle colour curves remain opaque.
Do not guess a green material override or re-enable the rejected ground fire.
An isolated controller/package/lifetime prototype can reuse the measured
crystal anchor and existing cleanup rules without creating art, but it needs
separate reviewed engineering and an eventual written visual verdict. No
shipping particle, material, artist asset or package was changed by this audit.
The original small linked-flame feature remains blocked.
