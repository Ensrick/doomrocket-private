# Doomrocket sound test protocol

This is the acceptance gate for the custom Doomrocket sound bank. The candidate
contains twelve approved assets: the living Bombardier's backpack loop, the
launcher shot, a ground-body plus air-crack pair played together for every
rocket detonation, six combat-voice variants (five spoken barks and one laugh),
and two death takes. Passing offline checks proves the bank is present and wired;
it does not prove spatialisation, occlusion, replication, variation, or cleanup
inside Vermintide 2.

A separate bespoke pre-fire cue, rocket flight loop, and insertion/latch sounds
are still future assets. The combat pool currently begins at the replicated
projectile-launch boundary and is limited to one bark per five seconds for each
Bombardier, preventing a three-rocket volley from stacking three lines. The
recordings are temporary pending a better capture environment. Any inherited
Ratling death vocal or Warpfire projectile hiss is a regression. The native
Warpfire-backpack explosion is the deliberate crash-safe impact fallback while
the custom bank is unavailable; it is acceptable only when the log also says
`phase=impact_config status=fallback`.

## v0.1.59 runtime failure and v0.1.60 containment

Two complete tester logs from 2026-09-01 established the actual failure rather
than relying on offline inference:

- `v0.1.59-dev` loaded `wwise/doomrocket`, but `Wwise.has_event` returned false
  for every attempted custom event: backpack, launch, impact, combat voice, and
  death voice. The inherited Globadier/Ratling-family death sound was the only
  audible result.
- Both rocket impacts crashed inside `wwise_pluginw64_release`. The Lua stack
  was `WwiseWorld.make_auto_source` -> `WwiseUtils.make_position_auto_source`
  -> `DamageUtils.create_explosion` -> `ProjectileRocket.rocket_explode`, with
  `wwise_world=nil`.
- The cause was a direct mod call to `DamageUtils.create_explosion` using
  `Unit.world(projectile)`. That Stingray world handle was not registered with
  `Managers.world`, so the audio branch could not resolve a Wwise world.

`v0.1.60-dev` contains the crash independently of custom-audio success:

1. Projectile and loaded-warhead death explosions call the game-owned
   `AreaDamageSystem:create_explosion`. That system supplies its managed level
   world, performs the authoritative explosion once, and owns client
   replication.
2. The explosion template uses the custom impact event only when
   `Wwise.has_event` confirms it registered; otherwise every peer selects the
   known native Warpfire impact event.
3. Every direct custom unit-audio path resolves and validates
   `Managers.world:world("level_world")` and its Wwise world before calling
   `WwiseUtils`. A missing world fails silent with telemetry rather than
   crossing into the native plugin with nil.
4. The package now includes the Wwise 2018.1 `Init` bank omitted by v0.1.59.
   Its SHA-256 is pinned and it is byte-identical to the Init product shipped
   by two independent, working VT2 custom-audio mods. This is a sound-fix
   candidate, not proof: only a new game log showing `status=played` proves the
   Doomrocket events registered.

## Reproducible bank build

The VT2 SDK does not include the historical Wwise 2018.1 authoring application
or Fatshark's Wwise exporter. The deliberately small bank is therefore built
from documented version-132 structures by
`tools/build_doomrocket_wwise_bank.py`; the main bank does not copy donor media
or donor HIRC objects. The builder also emits the pinned, standard Wwise 2018.1
Init product described above. The twelve hash-pinned masters under
`audio_src/doomrocket/` are the source of truth, never whichever similarly
named files remain in Downloads.

Rebuild from the repository root with:

```powershell
py -3 tools/build_doomrocket_wwise_bank.py `
  --source-dir audio_src/doomrocket `
  --repo-root .
```

This rewrites the main bank, the Wwise `Init` prerequisite, their four
Stingray metadata/dependency products, and
`wwise/doomrocket.bank_manifest.json`. For the current approved masters, the
wrapped bank SHA-256 is
`50e9d0c4ae2fec24ede1e5b2c6eb302644046d8ffc35433202d9e48a60027fc9`.
The offline gate below performs a clean-room rebuild in a temporary directory
and requires every generated byte to match. If Crunch supplies a replacement
asset, update the approved source hash and expected bank evidence deliberately;
do not bypass this comparison.

## Offline gate

From the repository root, run:

```powershell
py -3 tools/tests/test_doomrocket_sound_contract.py
powershell -NoProfile -ExecutionPolicy Bypass -File tools/Test-WarlockPipeline.ps1
git diff --check
```

The focused test rejects a candidate unless:

- the package actively includes `wwise/*`;
- the main and Init banks, both dependency descriptions, bank metadata, and
  project metadata all
  exist, use VT2's observed Wwise 2018.1/version-132 bank format, and expose
  the same twelve `Play/Stop_enemy_doomrocket_*` events;
- the runtime loads `wwise/doomrocket`;
- launch, backpack, combat-voice, and death-voice paths no longer call borrowed
  Warpfire or Ratling death events; the replicated impact alone has one
  explicitly gated native fallback;
- one authority-selected combat variant is carried through the existing launch
  RPC and played at the Bombardier's head on every peer, with a per-enemy
  cooldown and no immediate repeat;
- both unit and husk death reactions select one custom death take, suppress
  hot-join playback, and explicitly disable the inherited Ratling death event;
- each server-owned projectile or loaded-warhead explosion calls the
  game-owned `AreaDamageSystem` exactly once, with no direct `DamageUtils`
  invocation or hand-written explosion RPC;
- no custom-audio helper passes `Unit.world(...)` into `WwiseUtils`; the
  managed level world and its Wwise world must both exist first;
- the backpack has both start and stop wiring and every mod/level teardown
  reaches an idempotent audio cleanup path;
- when source WAVs are retained under `audio_src/doomrocket/` or `wwise/`,
  they are the twelve approved mono 44.1 kHz/16-bit files, contain no `smpl` chunks,
  and match the recorded handoff hashes.
- when `bundleV2` exists, it contains exactly one compiled main bank, Init
  bank, matching dependency for each, and project-metadata resource; both
  compiled banks' raw bytes must equal their authored products exactly, and
  the compiled event metadata must retain the backpack's `Infinite` flag and
  all eleven one-shot flags.

### Bank-version evidence

The version gate comes from two independent artifacts; it is not a successful
parser guess. The current VT2 SDK `bin/plugins/wwise_pluginw64_dev.dll`
(SHA-256
`4A1EB054BC5E631EE75302F2CA61636F4BF4FC8648585722BF701BEAEA78DC08`)
contains the little-endian XOR word `0x9211BCAC` at file offsets `0x15026` and
`0x1510F`. The native Ratling bank and the proven Pusfume and Loremasters'
Armoury custom banks all store `0x9211BC28` in the first BKHD generator field.
The recovered generator version is therefore:

```text
0x9211BC28 XOR 0x9211BCAC = 0x00000084 = 132
```

The test independently requires the proven stored word and this XOR result.
Merely forcing a third-party parser to interpret the bank as version 132 or
134 is not accepted as evidence.

## Packaging gate

Use the repository's complete build order:

1. Run a clean VMB/VMBLauncher build of `doomrocket` without deploying or
   uploading.
2. Run `tools/splice_warlock_materials.ps1`. A clean SDK build regenerates the
   five character child materials, so omitting this established post-process
   regresses the reviewed armor/skin/fur/whisker bindings.
3. Run `tools/Test-WarlockPipeline.ps1` again against the finished
   `bundleV2`. It must report the compiled Wwise bank, dependency, and metadata
   checks plus all model, texture, weapon, combat, ballistics, and ragdoll
   gates as passing.
4. Only then deploy the exact `bundleV2` artifact. Uploading the public
   Workshop item is a separate, explicit publication action.

All host and client participants must run that exact resulting Workshop/local
artifact. Restart the game after deployment so a previously loaded sound bank
cannot mask a stale build.

## Baseline single-enemy pass

Use one Bombardier in an otherwise quiet, open area. Record video and retain
the complete console log.

1. Approach from roughly 30 m to 15 m and then 5 m. The backpack must sound as
   though it originates at and follows the living enemy. It must attenuate
   naturally with distance rather than remain head-locked or equally loud.
2. Put a solid wall between the listener and enemy. The loop should obey the
   game's normal obstruction/occlusion treatment, then recover after line of
   sight returns.
3. Circle the stationary enemy. The sound image must track its direction and
   must not jump, split into disconnected left/right sources, or follow the
   camera.
4. Let it complete three full fire/reload cycles. Each rocket must produce
   exactly one muzzle-localised launch sound. There must be no continuous
   flamethrower hiss before or after it.
5. Across repeated volleys, hear at most one combat bark per Bombardier every
   five seconds. It must originate from the enemy, match on host and client,
   avoid immediate repetition, and never stack once per rocket. The laugh is a
   normal member of this pool.
6. Detonate one rocket on level terrain. Exactly one explosion must occur at
   the impact position. Listen for both the solid ground/body component and
   wider air/crack component when the log selected the custom event; they are
   layers of one event, not alternatives. When the log selected the native
   fallback, require exactly one audible Warpfire impact instead.
7. Shoot one incoming rocket. It must use the same layered impact event exactly
   once at the mid-air detonation position.
8. Let one rocket miss or hit distant geometry. Audio must remain at the real
   detonation position, not at the shooter, target, or listener.
9. Repeat Crunch's two crash repros: enable AI with one dead and one living
   Bombardier, then separately push a living Bombardier and allow its rocket to
   explode. Both must remain crash-free. Preserve the full log and confirm it
   contains neither `WwiseWorld.make_auto_source` with a nil Wwise world nor a
   direct Doomrocket `DamageUtils.create_explosion` stack.

## Lifecycle and stress pass

1. Kill a Bombardier while merely idling, during launch wind-up, immediately
   after launch, and after it fires. Its backpack must stop once, with no
   machinery left at the corpse or original spawn point. The rocket and its
   eventual impact must continue normally when appropriate. Exactly one custom
   death take must play from the dying enemy; no Ratling death line may overlap.
2. Spawn and kill five Bombardiers rapidly. Count one living loop per enemy;
   after all five die, none may remain. New spawns must still produce sound.
3. Move far enough to force ordinary despawn, then return. There must be no
   orphan loop and no silent replacement enemy.
4. Join an already-running host as a remote client while a Bombardier is alive.
   The joiner must hear one backpack loop—not zero and not two—and both peers
   must hear subsequent launch and impact events once.
5. Leave and re-enter `StateIngame`, then repeat one spawn/fire/kill cycle.
   This checks bank/runtime reset and stale playing-ID cleanup.
6. Repeat at least one full cycle after a mod hot reload if the development
   setup supports it. Do not use hot reload as the only test; bank replacement
   itself requires a fresh game process.

## Host/client acceptance

Run at least three ordinary shots, one shot-down rocket, one enemy death, and
one five-enemy cleanup on both a listen host and a remote client. Pass only if:

- both peers hear one backpack loop per living Bombardier, matching combat and
  death variants, and one launch and one layered impact per rocket;
- position, attenuation, and occlusion are plausible on both peers;
- death, despawn, level exit, disconnect, and hot join leave no orphan or
  duplicate loop;
- launch/impact damage, ballistics, aiming, shove behavior, textures, weapon
  placement, and ragdolls show no regression;
- neither log contains `Failed to trigger event`, `Script Error`, `assertion
  failed`, a native access violation, an invalid playing/source ID, or either
  `warpfire_thrower_shoot_end` placeholder warning.
